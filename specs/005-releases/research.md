# Research: Releases

Consolidates protocol research (sentry-cli's real command surface and REST API, researched against
docs.sentry.io/develop.sentry.dev and sentry-cli's own documentation) and the scope decisions made
from it, plus engineering decisions this module's design required beyond what protocol research
alone could settle. Written in the same decision/rationale/alternatives format as Modules 2-4's
research.md.

## 1. sentry-cli release-management command surface → REST endpoints

**Decision**: implement the confirmed endpoint shapes directly, no invented ones:

| Command | Method | Path |
|---|---|---|
| `releases new <version>` | `POST` | `/api/0/organizations/{org_slug}/releases/` — body `version`, `projects: [slugs]`, optional `ref`/`url`/`dateReleased`/`commits`/`refs` |
| `releases files <version> upload-sourcemaps <path>` | `POST` | `/api/0/projects/{org_slug}/{project_slug}/releases/{version}/files/` — multipart: `file`, optional `name`/`dist`/`header` |
| `releases finalize <version>` | `PUT`-equivalent | sets `dateReleased` on the release |
| `releases set-commits` | `PUT`-family | associates commit data with a release |
| `deploys new --release <v> -e <env>` | `POST` | creates a deploy record associated with the release |
| `releases list` / `delete` / `propose-version` | `GET`/`DELETE`/`GET` | both org- and project-scoped variants confirmed for list/retrieve/update/delete |

Auth: `Authorization: Bearer <SENTRY_AUTH_TOKEN>` — this is the exact header shape FlightDeck's new
`apiTokenAuth` middleware (§4) must accept.

**Source**: https://docs.sentry.io/product/cli/releases/,
https://docs.sentry.io/api/releases/create-a-new-release-for-an-organization/,
https://docs.sentry.io/api/releases/upload-a-new-project-release-file/,
https://docs.sentry.io/api/releases/

## 2. Config discovery: `SENTRY_URL` is overridable — no protocol gap

**Decision**: no FlightDeck-specific CLI wrapper needed — a real, unmodified `sentry-cli` installation
works by having the customer set `SENTRY_URL` to FlightDeck's own domain.

**Rationale**: confirmed directly — sentry-cli reads config in priority order (CLI flags → env vars
→ `.sentryclirc` → `.env`), with `SENTRY_AUTH_TOKEN`/`SENTRY_ORG`/`SENTRY_PROJECT`/`SENTRY_URL` all
overridable via env var or `.sentryclirc`'s `[auth]`/`[defaults]` sections. This is the exact same
"point existing tooling at a new endpoint, no code change" pattern Module 2 already achieved for
SDKs via DSN — spec.md's SC-001/SC-005 depend on this holding, and it's confirmed, not assumed.

**Source**: https://docs.sentry.io/product/cli/configuration/

## 3. The org-slug problem: resolved — accept as a pass-through constant

**Decision**: FlightDeck's release routes accept `{org_slug}` in the URL path for every endpoint
that requires it, but never validate it against a real organization registry — it's a required,
substantively-ignored path segment. Release CREATION (the one operation confirmed to have no
project-scoped equivalent) resolves which real FlightDeck project(s) a release belongs to from the
request BODY's `projects: [slugs]` array, not from the URL's org-slug.

**Rationale**: every release-FILE operation (upload/list/retrieve/update/delete) has a confirmed
PROJECT-scoped path variant (`/api/0/projects/{org_slug}/{project_slug}/releases/...`) mapping
directly onto FlightDeck's existing project model. This is a genuine, researched resolution, not a
hand-wave — FlightDeck doesn't need to invent an organizations feature (explicitly out of scope,
spec.md's Assumptions) to be sentry-cli-compatible, because sentry-cli's own protocol already
carries the real routing information (which project(s)) in the request body for the one endpoint
that's org-scoped only. This divergence — accepting but not validating `org_slug` — is exactly the
kind of "necessary, named divergence" constitution Principle IV requires be documented explicitly,
not silently assumed.

**Source**: https://docs.sentry.io/api/releases/ (endpoint listing confirms path-variant coverage)

## 4. API tokens: an extension of the control-plane trust surface, not a third one

**Decision**: `Authorization: Bearer <token>` authentication for the sentry-cli-facing endpoints,
via a new `apiTokenAuth` middleware (parallel to `worker/auth/session.ts`'s `sessionAuth`, not a
replacement for it). Tokens are generated by an authenticated, `sessionAuth`-verified human via the
dashboard, stored as a salted hash (never plaintext — the raw value is shown once at generation
time and never retrievable again), revocable, and every release-management action performed via a
token is `audit_log`-recorded attributing the actor as the token's owning account.

**Constitution reasoning (required explicitly, not skipped)**: constitution Principle I defines
"Two Trust Surfaces" as the Access-gated control plane versus DSN-authenticated, anonymous, public
ingest. An API token is NOT a third surface — it is the control-plane surface's authorization,
carried in a form (`Authorization: Bearer`) that a non-browser CI/CD client can hold, since such a
client can't maintain a live `fd_session` cookie. The trust boundary this represents is identical to
session auth's: "an authenticated human account authorized this action" — only the credential FORM
differs, chosen for the client type (browser vs. CLI), not the authorization model. This is
distinct in kind from DSN-key ingest auth, which is deliberately anonymous and public by design
(any SDK holding a DSN can submit events, no account backing it) — a DSN key could never be used to
delete a release, and an API token could never be used to submit anonymous SDK events; the two
remain cleanly separated exactly as Principle I requires, just as `sessionAuth` and DSN auth already
are today. No constitution amendment needed — this is a within-scope extension of an existing
principle's control-plane half, reasoned through explicitly rather than assumed.

**Scope of a token**: project-level, matching sentry-cli's own `SENTRY_PROJECT` usage (a real
`sentry-cli` invocation is configured against one project per CI pipeline/repo, not an
organization-wide credential) — an `api_tokens` row references one `project_id`, not an
account-wide scope. This also bounds the blast radius of a single leaked token to one project's
release data, consistent with least-privilege reasoning already applied to Module 2's GitHub App
credential and Module 4's R2 export credentials.

## 5. Release health ingest: a 4th distinct envelope item type, direct D1 writes

**Decision**: `worker/modules/ingest/envelope.ts` gains `isSessionItem()`, dispatching on `"session"`
(one session) or `"sessions"` (a pre-aggregated batch) — both feed the same aggregation function,
folding into a daily UPSERT against a new `release_health` table
(`project_id`, `release_id`, `environment`, `date`, `sessions_total`, `sessions_crashed`,
`sessions_errored`, plus §6's distinct-user mechanism). No Cloudflare Queue — direct D1 writes,
unlike Modules 3-4.

**Rationale**: Sentry's own SDK guidance is that "Server-mode SDKs SHOULD pre-aggregate closed
sessions before sending" — client-side aggregation already keeps FlightDeck's request volume down
to something much closer to Module 2's error-ingest volume (one request per aggregation flush
interval, not one per individual session) than Module 4's raw-log volume. Writing one D1 row per
DAY per (project, release, environment) — not per session, not per request — keeps this comfortably
within D1's free-tier write budget even under real usage.

**Source**: https://develop.sentry.dev/sdk/telemetry/sessions.md

## 6. Distinct-user counting: a bounded, capped exact table — not HyperLogLog

**Decision**: a small `release_health_users` table (`project_id`, `release_id`, `environment`,
`date`, `did`), deduplicated via `UNIQUE(project_id, release_id, environment, date, did)`, capped at
a hard limit (10,000 distinct `did` values tracked per project/release/environment/day). Below the
cap, `users_total`/`users_crashed` are exact counts (`COUNT(DISTINCT did)` scoped to that day's
rows, or a maintained counter incremented on each successful insert). At/beyond the cap, further
distinct-user inserts for that bucket are simply skipped (session/crash counters in `release_health`
keep incrementing normally) and the UI shows the count as "10,000+" rather than a false-precision
exact figure past the point FlightDeck stopped tracking new distinct IDs.

**Rationale — reasoned through explicitly, not hand-waved**: a naive unbounded per-day
distinct-`did` table is itself a write-volume risk at real scale (every NEW distinct user on a busy
day is one insert) — but capped at a number far above what any early-stage product's daily active
users would realistically be, it stays bounded and simple. A HyperLogLog-style probabilistic sketch
was considered (genuinely closer to what Sentry itself likely does internally, and unbounded in
principle) but rejected for this module's scope: it requires either a new dependency (no off-the-
shelf pure-JS HLL implementation was verified to exist and fit this project's Deno-only,
no-new-npm-dependency posture without further research) or a nontrivial from-scratch
implementation, for a metric (crash-free USER rate) that is explicitly secondary to crash-free
SESSION rate (spec.md's FR-005/FR-006 name both, but session rate needs no distinct counting at all
— every session row is already a discrete event). A capped exact table is the honest, simple,
MVP-appropriate choice — explicitly flagged as an approximation past the cap rather than presented
as exact forever, the same honesty standard applied to Module 4's R2-token-scoping and Module 2's
source-map-library uncertainty.

**Alternatives considered**: unbounded exact table (rejected — genuine unbounded write-volume risk
at real scale, the same category of problem Module 4's research identified for raw log lines, just
at a different multiplier); HyperLogLog sketch (rejected for now — real technique, but adds
dependency/implementation risk this module's scope doesn't need yet; worth revisiting if actual
usage ever approaches the 10,000-per-day cap in practice, which would itself be a signal FlightDeck
has outgrown MVP scale generally).

## 7. Regression detection: extends Module 2's existing error-ingest path

**Decision**: after Module 2's existing issue-upsert logic in `worker/modules/ingest/routes.ts`
(the `"event"` item handler), a new check: if the issue's `status` is `resolved`, compare the
ingested event's `release` against the release referenced by the resolution
(`resolved_release_id`), ordered by the `releases` table's creation order (or `date_released` once
finalized — whichever is the more meaningful "later" for the two resolution modes, decided per
mode: exact-release resolution compares against that release's own position; "resolved in next
release" compares against whichever release was created immediately after the resolution). If the
new event's release is later, flip `status` back to `unresolved`. If it's the same or earlier, no
change — this is NOT a regression, per spec.md's Edge Cases.

**Rationale**: this is confirmed as a well-defined, replicable rule from Sentry's own documented
behavior — "newer by creation/finalization order," not a raw timestamp comparison (a release
finalized out of chronological upload order should still compare correctly by its actual release
ordering, not by when its files happened to be uploaded). Implementing this as an extension of the
EXISTING ingest path (not a new endpoint or a scheduled job) keeps regression detection real-time,
consistent with how errors already become visible within seconds (Module 2's spec SC-001).

**Source**: https://www.sentry.help/en/articles/13964279-why-didn-t-my-issue-regress-after-i-resolved-it-in-a-release

## 8. Testing: hand-crafted requests for automated tests, real `sentry-cli` for manual quickstart

**Decision**: automated contract tests (`tests/contract/`) use hand-crafted HTTP requests matching
the exact confirmed endpoint shapes (§1) — the same "hand-crafted request matching the real
grammar" pattern Module 2 already established for envelope contract tests, not a dependency on
installing the real `sentry-cli` binary in CI. `quickstart.md`'s manual validation step DOES use a
real `sentry-cli` installation, run by a person, for the actual end-to-end confidence this module's
core promise (SC-001/SC-005) needs — matching how Module 2's quickstart also offers "configure a
real SDK" as the primary validation path alongside its contract-test fallback.

**Rationale**: `sentry-cli` is a compiled binary (not an npm package importable via Deno's `npm:`
specifier for in-process testing) — installing and invoking an external binary from automated tests
would add real CI-environment provisioning complexity (a curl-based install step, PATH management)
for marginal benefit over hand-crafted requests that already exercise the identical wire format.
Reserving the real binary for human-run quickstart validation, not automated CI, is the same
tradeoff Module 2 made for its own contract-vs-real-SDK testing split, applied consistently here.

## 9. Frontend: releases list/detail, resolve action, no regression-history table

**Decision**: `ReleasesScreen.tsx`/`ReleaseDetailScreen.tsx` follow the established list→detail
component-state navigation pattern (Module 2 onward). A "regressed" indicator on an issue is
inferred from its CURRENT `status` (an issue that is `unresolved` but has a non-null
`resolved_release_id` has, by definition, regressed at some point) — no separate regression-history
table is needed, since spec.md's acceptance scenarios only require showing current status, not a
timeline of past regressions. Adding one now would be scope creep against an unstated requirement,
the same reasoning Module 2 applied when declining to add resolve/ignore/assign UI beyond what its
own FRs actually needed.
